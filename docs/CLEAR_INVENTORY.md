# 清空当前库存与默认采购日期

## 使用

### 清空当前库存

「冰箱」页面底部展开“清空当前库存”，核对显示的有库存批次数及家庭范围，填写原因，并输入 **清空库存** 四个字。点击“确认清空当前库存”才会执行。

该操作将整个家庭所有正库存批次的剩余量归零；两位家庭成员都可操作，库存为家庭共享。每个批次增加一条 ADJUSTMENT 流水，记录真实操作用户、时间、原数量的负差量、清空后的 0 和原因。不会删除食材目录、批次、采购单、价格或旧流水，不会把所有清空擅自归类为食物报废。

清空后默认冰箱列表不显示零库存食材，可勾选“显示零库存食材与历史批次”查看记录。没有一键撤销；若要恢复需按真实数量进行有审计的批次盘点调整。清空只影响现有库存，不会重写购物清单中历史已入库的完成记录。

只减少某一批次时，原有「冰箱 → 食材详情 → 盘点调整 / 报损」仍可使用，输入调整后的剩余数量（包括 0）和原因即可。做饭 FEFO 扣减仍在后续阶段。

### 默认当天采购日期

所有新采购核对单使用当前设备的本地日历日期，不用 UTC 日期切片，避免时区跨日导致默认成昨天/明天。手动采购、文字导入、历史“再买一次”和购物清单转入的新采购都会显示当天。

日期仍可手动改为实际购买日期。已保存草稿中的非空日期保留，不会在刷新/次日自动改动。用户主动清空日期也会保留空值，提交前仍需选一个合法日期。旧版草稿的空日期在未手动清空的情况下会自动填今天。

完成后点击“再记一笔采购”会重新默认当天；“继续处理未勾选商品”是同一小票的后续处理，保留该小票已填写的购买日期。历史再次购买不会复制原小票旧日期，默认今天。解析区本身不写数据库，日期在核对单中确认。

## 上线步骤

1. 在原 Supabase 项目的 SQL Editor 新建查询，执行新增 `supabase/migrations/202610260004_clear_inventory.sql` 一次。
2. 不重跑 001–003，不删表或重建家庭。这份迁移只新增清空函数/私有幂等日志，并扩展库存快照，**执行迁移不会清空实际库存**。
3. 通过 PR 合并本分支到 main，等 CI 和 Vercel 部署。原 Supabase 环境变量保持不变，无需新密钥。
4. 迁移未执行时原库存/采购仍可读取，页面提示清空功能需要迁移，不提供会假成功的按钮。日期默认功能不需要修改数据库。

## 事务与并发保护

库存快照新增 `clear_fingerprint` 和 `positive_lot_count`：在同一条数据库语句中，以正库存批次 ID、数量和更新时间 epoch 值计算 SHA-256 摘要。确认请求仅传摘要，不需要上传整库批次列表，也不接受客户端指定家庭。

`clear_inventory` 从 auth.uid() 推导当前家庭并重查成员关系，锁家庭行，与采购、调整及购物清单入库的锁顺序一致。只有摘要仍与当前库存一致才执行。新增入库、调整或其他清空会使旧确认失效；此次请求不会清掉部分或刚到货的食材。摘要使用 epoch，避免数据库会话时区影响。

库存归零、所有流水和私有请求日志一次事务提交。请求编号/载荷保护网络重试；成功清空后即使又有新采购到货，使用原编号重试只返回原结果，不再执行清空。相同编号改变摘要/原因会拒绝。日志表启用 RLS 且不给客户端读写权限，匿名调用不能执行清空。

公开浏览器请求不能绕过家庭隔离；拥有数据库管理员权限者不在普通客户端权限边界内。迁移和测试均未对真实用户库存执行清空。

## 检查与线上验收

本机测试包括清空保留历史、逐批审计、家庭隔离、并发旧摘要拒绝、成功后新增库存不受重试影响、注入最终日志错误时整单回滚，以及默认本地日期、手动日期/草稿保留、确认与离线阻止行为。真实 PostgreSQL 集成测试使用隔离 Docker 容器，不访问生产数据库。

线上验收由用户在明确要清空时执行：

1. 先核对采购和库存历史，再展开清空确认。不要为了测试清空仍在使用的真实库存。
2. 只有输入准确确认文字并提交，库存才应归零；采购历史与流水仍可查看。零库存开关可找回食材详情。
3. 两人同时使用旧确认时，一方应收到“库存已变化”，不能再清掉对方刚入库的数据。
4. 新采购默认当天；手动选过去日期后刷新仍保留；下一笔全新采购重新默认当天。

代码和本地检查通过不代表已完成托管迁移、部署或用户实际清空验收。
