1. 在现有 Supabase 项目的 SQL Editor 执行 **新增**迁移 `supabase/migrations/202610260002_inventory.sql` 的完整内容一次。
2. 不重复执行 `202610260001_households.sql`，不删除已有表，不重建家庭；新迁移只创建库存相关表和函数，并请求 PostgREST 刷新 schema cache。
3. 通过 PR 合并本分支到 main，等待 CI 与 Vercel 正式部署成功。Vercel 使用已有两个 Supabase 公开环境变量，无需管理员密钥或新外部服务。
4. 按下列步骤在正式网站验收。代码构建、测试通过不等于迁移和托管双账号验收已经完成。

如果新代码先上线但迁移未执行，页面会显示“库存读取失败/确认迁移”，不会显示假库存或假入库成功；账号与家庭功能继续保留。

## 日常使用

- 首页：从数据库显示家庭、昵称、成员数；读到库存才显示真实数量。未登录、未加入家庭、未配置和读取失败分别提示。菜单和共享购物清单尚未实现，明确标注待开放。
- 「采购」→「记一笔采购」：选择采购日期、可空商店/备注；每行选择已有食材或填写新名称及分类、基础单位、数量、可空行总价、可空到期日及存放位置。可添加/移除商品行，最多 50 行。
- 数量使用基础单位（g、ml、个、包、袋、瓶、盒、份）。1kg 请填 1000g，不能把“个”按猜测换成“g”。已存在的同名食材沿用原单位，不会静默创建两个单位冲突的目录项。
- 金额默认美元，是整行商品价格；未知留空，0 表示实际免费。小计存在缺价时不会冒充整单总价。未知保质期保持 null，不虚构日期。
- 入库后查看采购单、批次及流水。同一名称多次采购会产生多个批次，库存按同一基础单位累计。
- 冰箱支持名称搜索、分类和保质期筛选。临期定义为当前设备日期到未来 3 天（含今天）；已过期与未知到期日单独标记。总库存包含所有批次，不等于可食用量。
- 食材详情显示批次、来源、价格和最近 100 条流水。可对单个批次盘点或报损：输入**调整后剩余数量**及原因。报损只能减少数量，库存不可为负。
- 采购历史显示最近 20 单，详情最多 50 项（与每单上限一致）。库存快照不受 PostgREST 顶层行数限制截断；库存数据量增长后应进一步做目录分页和服务端汇总。

## 重试、草稿与共享

采购草稿和请求编号按家庭/用户隔离，暂存在当前浏览器标签页的 sessionStorage；不会自动上传。输入过程保存同一草稿，网络失败后重试仍使用同一请求编号。成功后保存已确认标记，刷新不会再次提交；“再记一笔”才生成新编号。

不要在结果不确定时主动清除草稿/浏览器存储或换设备重建同一采购；请求编号改变后系统无法判断两张看似一样的小票是否是同一笔购买。多个标签页人为新建相同采购也属于不同请求，不是幂等机制能自动合并的重复。

本轮是刷新共享：两人刷新即可读到数据库最新内容，未实现 Realtime 推送。调整带原库存值；另一成员已更新时拒绝旧值覆盖，提示刷新后重新核对。采购未登录、缺少家庭、数据库错误、离线或无法保存草稿时均不会假装提交成功。

## 数据库设计

新增 ingredients、purchases、purchase_items、stock_lots、stock_movements，UUID 主键，NUMERIC 数量/金额、检查约束、索引、更新时间和 RLS。家庭相关引用使用组合外键 `(household_id, id)`，防止跨家庭食材/采购单/批次关联。所有 client 表写入权限撤销，只有受限 RPC 可以修改库存。

- `record_purchase(request_id,payload)`：以 auth.uid() 获取真实家庭，锁定家庭行，检查同一请求号与载荷哈希，原子创建采购、明细、食材、批次和 PURCHASE 流水。任意一行失败整单回滚；请求重试返回原结果，同编号不同内容拒绝。
- `adjust_stock(...)`：锁定家庭和批次，校验原库存值，记录 ADJUSTMENT/WASTE 的差量及调整后余额；先检查幂等结果，再检查旧值，避免成功请求的网络重试再次调整。
- `read_inventory()`：SECURITY INVOKER，单条 SQL 返回同一快照的食材和批次，仍受调用者 RLS 限制；移除家庭后不能继续读取该家庭库存。
- 流水为只追加，客户端不能修改/删除，触发器也阻止意外的 privileged UPDATE/DELETE。未来实现家庭删除/个人数据清理时需显式设计审计保留策略，不应绕过该保护。

家庭行锁对两人家庭足够，避免跨表竞态；不会锁住其他家庭。做饭/FEFO 暂未开放，COOK 仅为后续预留的流水类型，不能宣称已验证做饭扣库存。

## 可复现检查

```sh
npm ci
npm run lint
npm run typecheck
npm test
npm run test:postgres
npm run build
```

`npm test` 包括真实 PostgreSQL 引擎 PGlite 的 RLS/事务测试、服务端操作/状态验证和采购表单的草稿/重试交互测试。

`npm run test:postgres` 需要 Docker。脚本只创建自己命名的临时 PostgreSQL 17 容器，使用 loopback/容器内 Unix socket，不发布端口、不连接生产数据库，结束后清理容器。验证四种真实多连接场景：同请求同时入库、同号不同内容、过时库存并发调整、整单回滚。CI 增加独立并发检查任务。

Playwright 的当前基线针对未配置环境，避免对生产数据写入：构建和启动测试都将 `NEXT_PUBLIC_SUPABASE_URL`、`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` 置空；例如：

```sh
NEXT_PUBLIC_SUPABASE_URL= NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY= npm run build
NEXT_PUBLIC_SUPABASE_URL= NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY= PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:e2e
```

完成基线后，运行正常的 `npm run build` 恢复使用当前真实配置的构建。没有把生产账号密码或管理员权限写进测试。

## 正式站点验收（待用户执行）

1. 现有账号登录，首页显示实际家庭名称、昵称和成员数，不再误报“待连接”。
2. 第一单录入鸡蛋 12 个，价格 4.99，到期日留空；确认后采购单、冰箱及批次均存在，保质期显示未知。
3. 第二单录入同一鸡蛋 6 个，指定到期日；总量应为 18 个、两个批次，刷新后保留。
4. 第二位已入家成员在独立浏览器刷新，应读到相同库存，并可新增采购。不要将账号密码发给开发者。
5. 将一个批次盘点调整或报损，核对新余额、差量、原因及操作用户；另一浏览器使用过时值调整时应被拒绝。
6. 断网提交不得显示成功；恢复连接后使用原草稿重试，不得多出一笔采购。
7. 外部账号不能读取或引用本家庭食材/批次。此项已由数据库自动化验证，托管账号流程仍需完成。
