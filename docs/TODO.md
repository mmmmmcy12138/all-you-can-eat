## 下一轮优先：消除页面状态与真实家庭不一致

当前已创建家庭后，首页仍显示“待连接厨房”，冰箱/点菜/采购仍提示“尚未连接 Supabase”。这些是基础界面遗留文案，不能再用来描述已经连通的账号系统。

- [ ] UX-01：用真实会话和家庭关系区分“未登录 / 未加入家庭 / 已加入但无记录 / 对应功能未开放 / 读取失败”。已连接家庭不显示“未连接”。库存模块未实现时不能将未知库存显示成 0。
- [ ] UX-02：首页展示真实家庭名称、本人昵称和成员状态；下一步按钮按状态显示“登录 / 创建或加入家庭 / 录入第一笔采购”。
- [ ] UX-03：未开放功能给出具体说明；相关入口保持可解释，不让用户以为按钮能完成尚未实现的保存。
- [ ] UX-04：统一加载、空状态、提交中、成功和失败反馈；离线时明确不能确认云端写入成功。表单切换后清除上一模式的提示，避免注册成功提示混入登录表单。

验收：已登录且有家庭的用户，在任何核心页面都不会被误报为“尚未连接 Supabase”；读取失败不能伪装成空库存。家庭数据仍由 RLS 保护。

## Phase 3：先做能真正记一笔账的库存与采购闭环

建议顺序是“手动录入 → 真实库存 → 多批次与流水 → 批量导入”，先让产品日常可用。

- [ ] INV-01：食材目录、分类、基础单位和家庭内食材 ID；搜索现有食材避免重复录入。只有有明确换算关系的单位才能自动转换（如 kg/g、L/ml）；“个”和“g”不得擅自换算。
- [ ] INV-02：手动采购一笔食材，选择数量、单位、价格、采购日期、可空到期日、存放位置。价格为商品行总价、默认美元；未知保质期保持 null。
- [ ] INV-03：采购单、明细、库存批次和 PURCHASE 流水在同一个数据库事务写入，重复点击/重试不得重复入库；RPC 使用幂等键，校验同键不同载荷。界面实际呈现数据库保存结果。
- [ ] INV-04：同食材多批次累计总量，详情展示批次和流水；搜索、分类筛选、临期排序。过期/临期/未知日期分别展示，不擅自补保质期。
- [ ] INV-05：实现有备注的人工调整和 WASTE 记录。所有变动审计用户和数量，禁止绕过事务函数直接改余额，库存不为负。
- [x] IMP-01：文字导入器逐行验证，保留错误行号；预览中修改匹配食材、分类、单位、日期和入库勾选；有错误不能静默忽略。确认后复用同一采购事务。
- [ ] SEC-01：新表带 household_id、完整 RLS 与组合外键，阻止把别家的食材/批次 ID 写进本家；禁用绕过审计的普通客户端表写入权限。
- [ ] TEST-01：测试多批次总量、同键重试、同键不同载荷、无效明细整单回滚、跨家庭读写/引用拒绝、刷新持久化；并在具备环境后验证真实 PostgreSQL 多连接竞态。PGlite 串行测试不替代并发验收。

本阶段完成标准：两人能在网页中录入真实采购，刷新后看到同一份准确库存；重复点击不会多记，非法数据不会留下半张单据。
