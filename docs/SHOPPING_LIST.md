# 共享购物清单与历史再次购买

本轮在现有采购/库存上增加需求清单，用户和另一位家庭成员都可管理。不是 Realtime：提交后服务端重新读取；另一浏览器点击“刷新共享清单”或刷新页面查看变化。

## 上线步骤

1. 在原 Supabase 项目 SQL Editor **新建查询**，执行 `supabase/migrations/202610260003_shopping_list.sql` 的完整内容一次。
2. 不重跑之前的 001/002，不删除旧表或重建家庭。本迁移新增购物清单表、幂等日志及相关函数，不改写现有采购和库存记录，也不替换原 `record_purchase`。
3. 合并本分支 PR 到 main，等待 CI 和 Vercel 部署成功。无需新增密钥、修改邮箱模板或开新服务。
4. 线上按文末验收。迁移前旧手动采购/文字导入保持可用；新清单页面读失败时显示明确提示，不假装空清单或保存成功。

## 使用方式

- 「采购 → 打开共享购物清单」：选择已有食材或按名称添加需求。数量是**还需要的量**，使用 g/ml/个等基础单位。
- 同一家庭内同名活动商品合并，待买量取较大值、不相加。例如两人分别填写鸡蛋 12 个和 6 个，清单仍为 12 个。需要改成 18 个时进入详情明确修改剩余需求为 18。
- 不兼容单位不会合并。不能把“个”猜测换成“g”。已存在目录食材沿用其分类/单位，未出现的商品暂存清单，真正入库时才创建食材。
- 可以修改需求数量、标记“已买（未入库）”、改回待买或移除。移除是取消需求，不会扣掉冰箱库存；保留最近 20 项已处理记录。
- 标记已买只是购物进度，**不会增加库存**。新增更大的同名需求或修改数量会改回待买，请重新核对实际已购物品。本版不单独记录“已买未入库的部分数量”，部分购买以实际入库数量结算剩余需求。
- 勾选最多 50 项，点击“转入采购核对”。清单数量、食材和关联版本带入已有采购表单；价格与保质期留空，采购日期默认当前设备当天，均可按实际购买信息修改。
- 确认入库：一次事务创建采购/批次/流水，并更新这些关联清单行的已入库量。只买 5 个、原需求 12 个时保留 7 个；全买或多买后归档完成。未勾选、不在本次提交内的商品不变。
- 清单关联只应用于明确关联的那一行；另加的同名手动商品不会擅自冲抵需求。修改关联行的食材名称或 ID 会解除关联，也可以主动点“解除清单关联”作为独立采购入库。
- 若另一成员已经修改或入库该需求，旧核对版本会被拒绝，库存不变。先回清单核对最新状态；需要重选时移除旧草稿中对应行再从清单添加，或明确解除关联后作为独立采购。不会悄悄升级旧版本并扣减新需求。

## 历史“再买一次”

打开任一采购历史详情，点击“把这单加入新的采购核对”。仅复制食材 ID、数量、单位，商店作为可修改的默认值；不复制旧价格、旧采购日期、保质期或旧购物清单关联（新采购日期默认当天），不会立即写入库存。

存在未提交采购草稿时采用追加并保留原请求编号、原商店/日期/备注和勾选状态，不覆盖已填内容。超过 50 项或重复关联同一清单商品会阻止追加。上次成功采购还有未勾选商品时，也会阻止覆盖，需先在原核对页面处理或明确开始新采购。

再次采购是用户明确发起的**新购买**，会使用新的幂等请求编号，不能将其当作上一张小票的网络重试。草稿仍暂存在当前标签页 sessionStorage，不跨设备同步。

## 数据库边界

- `shopping_items`：household_id、可空 ingredient_id、名称/分类/单位、总目标 quantity、累计 stocked_quantity、状态、递增 version、创建/更新用户及时间。
- `shopping_requests`：调用幂等记录，只供受限函数使用，客户端不能读取或写入。
- 列表 RLS 与家庭隔离；复合外键禁止引用另一家庭食材。客户端没有直接表写入权限。
- `add_shopping_item`、`change_shopping_item`：从 auth.uid() 推导家庭，锁家庭行，校验请求编号/载荷及版本，避免重试累加、丢失并发修改或冒充成员。
- `record_purchase_from_list`：锁家庭/需求，检查旧版本、状态、唯一行号和关联；调用原采购事务，再验证真实明细的食材与单位后更新需求。任一步失败，采购、库存、流水和清单完成状态全部回滚。
- 同一清单需求被两人用不同请求编号同时入库时，只有一个旧版本能成功；相同请求重试返回原结果。同编号改变载荷或链接也会拒绝。
- `read_shopping_list`：SECURITY INVOKER 的单语句家庭快照，返回活动需求及最近 20 条完成/取消记录，不受 API 顶层行数截断。首页的待买/已买待入库数量来自同一真实数据源。

现有库存表、采购历史、邮箱配置和家庭数据均保留。未来菜谱缺料可以复用需求函数；本轮没有实现菜谱或做饭扣减。

## 验证与验收

自动化：PGlite 权限与事务测试、UI 草稿/提交测试、服务端鉴权测试，以及隔离 PostgreSQL 17 的真实多连接检查。`npm run test:postgres` 只操作测试容器，不接生产数据库。

正式站点验收（需用户执行）：

1. A 添加鸡蛋 12 个，B 刷新后可见；B 再添加 6 个，仍为 12，不是 18。
2. 标记已买，检查冰箱数量和采购记录都未增加。
3. 选中后转入采购核对，将实际量改为 5 个，填采购日期/价格并入库；查看库存 +5、清单剩 7。
4. B 刷新，看到相同库存与剩余需求。再入库 7 个后完成归档。
5. 两浏览器基于旧版本同时提交时，一方明确失败，不产生第二份库存。
6. 从历史“再买一次”，确认新日期/价格/到期日没有沿用，确认前库存不变。
7. 其他家庭不能读或修改这些清单记录，不能用别家的食材 ID 添加需求；断网或 RPC 错误不能显示已保存。

本轮本地自动化不替代托管数据库迁移、生产部署与真实双账号验收。
